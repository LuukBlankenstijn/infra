# OpenTofu roots

Every directory under `terraform/` is one OpenTofu root. The two-digit prefix is
the apply order on a fresh setup; equal prefixes are independent of each other.

## State

All roots use the same backend shape (`backend.tf`):

- S3 backend, bucket `luuk` on Hetzner Object Storage
  (`https://fsn1.your-objectstorage.com`, region `fsn1`), path-style,
  `use_lockfile = true` for locking;
- state and plan encryption enforced, `aes_gcm` with a PBKDF2 key derived from
  `var.state_passphrase`.

The root `.envrc` exports `TF_VAR_state_passphrase` from `secrets/tofu.yaml` and
`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` from `secrets/s3.yaml`. Each root's
`.envrc` runs `source_up` and adds only its own secrets.

Each root has its own state key, and no root reads another's state. Values one
root produces for another travel through OpenBao (for example the Authentik
client for NetBird) or the cluster (for example the provisioner passwords).

`50_pki` has two sensitive outputs, read with
`tofu -chdir=terraform/50_pki output -json <name>`: `host_approles` (AppRole
`role_id`/`secret_id` per host) and `phone_certificates` (certificate, key and
CA chain per phone). See [Observability](../observability/index.md#device-ca).

[OpenBao](../cluster/openbao.md#logging-in).

## What each root needs to reach

| Root | Needs |
| --- | --- |
| `10_edge` | Hetzner Cloud and Cloudflare APIs |
| `20_cluster-bootstrap` | the [LAN kubeconfig](../cluster/access.md#the-lan-kubeconfig) |
| `40_openbao-config`, `40_s3-buckets` | OpenBao at `https://openbao.luukblankenstijn.nl`, cluster access through the default kubectl context for the login token |
| `40_databases` | OpenBao; the LAN kubeconfig, to read `postgres/postgres-app` and `mariadb/mariadb-provisioner`; `192.168.1.78:5432` and `:3306` |
| `50_pki` | OpenBao, cluster access through the default kubectl context for the login token |
| `50_authentik-config` | OpenBao; Authentik at `https://auth.luukblankenstijn.nl` with the API token from `authentik/authentik-auth` key `AUTHENTIK_BOOTSTRAP_TOKEN`, read through the LAN kubeconfig |
| `60_netbird-config` | OpenBao (`authentik/netbird/netbird`); NetBird at `https://netbird.luukblankenstijn.nl` |

`AUTHENTIK_BOOTSTRAP_TOKEN` is generated by `40_openbao-config`. Authentik only
reads that variable on its first start, so the same value is also created as an
API token in Authentik with `ak shell`.

## Applying

```sh
mint-kubeconfig          # the LAN token lives 24 hours
cd terraform/<root>      # direnv loads the root's .envrc
tofu init
tofu plan
tofu apply
```

Applies run from the operator machine on the home LAN; CI never applies.

## Order on a fresh setup

1. `10_edge`, then deploy the edge host (see [Edge](../cluster/edge.md#deploying-the-host)).
2. `20_cluster-bootstrap` against the new node. Flux then reconciles the
   [layers](../cluster/layers.md).
3. `40_openbao-config` and `40_s3-buckets` once OpenBao answers. `services` stays
   unready until they have written the frpc token and the bucket credentials.
4. `40_databases` once Postgres and MariaDB run.
5. `50_authentik-config` once Authentik runs and its API token exists, and
   `50_pki` (it writes into the `secret` mount of `40_openbao-config`).
6. `60_netbird-config` once NetBird runs. `users.tf` applies after the user's
   first Authentik login.

`40_openbao-config` reads `api_token` and `proxy_token` from
`secrets/netbird.yaml`. Both are minted by a running NetBird (`/api/setup` for
the owner's token, `netbird-server admin token create` for the proxy token),
while NetBird itself needs `secret/netbird/server` from that root. After the
tokens are added to `secrets/netbird.yaml`, re-apply `40_openbao-config`.
